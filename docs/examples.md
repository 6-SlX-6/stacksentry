# Examples

All examples use the files in [`examples/`](../examples). Reports generated
from them are kept in [`examples/reports/`](../examples/reports) and are
regenerated by the test suite, so they always match the current rules.

## Scan an n8n + PostgreSQL stack

[`examples/n8n-postgres-compose.yaml`](../examples/n8n-postgres-compose.yaml)
is a typical self-hosting setup for the n8n workflow tool. Show only medium and
more severe findings, and fail on high:

```console
$ stacksentry scan compose examples/n8n-postgres-compose.yaml --severity medium --fail-on high
StackSentry v0.1.0
Target: examples/n8n-postgres-compose.yaml (project "n8n")
Scan time: 2026-10-01T12:00:00Z
Rules evaluated: 27 of 27
Services analyzed: 2
Findings: 0 critical, 1 high, 8 medium, 12 low

HIGH  SST-NET-001  postgres  (examples/n8n-postgres-compose.yaml:30)
  A database port is published on all host interfaces.
  Evidence: 5432:5432/tcp (PostgreSQL port published on all host interfaces)
  Why this matters: Published database ports are reachable from other machines and, on many Linux
    hosts, bypass host firewalls such as UFW or firewalld because Docker manages its own iptables
    rules. Databases reachable from the network are frequent targets of credential brute-forcing and
    ransom attacks.
  Fix: Remove the ports entry if only other containers need the database; they can reach it over the
    Compose network by service name. If host access is required, bind to localhost, e.g.
    "127.0.0.1:5432:5432". Exposure may be intentional, but it should be reviewed.

MEDIUM  SST-CFG-001  n8n  (examples/n8n-postgres-compose.yaml:7)
  The Compose file uses variables without a default value, so the deployment depends on external
  configuration.
  Evidence: ${POSTGRES_PASSWORD} has no default (examples/n8n-postgres-compose.yaml:19,
              services.n8n.environment.DB_POSTGRESDB_PASSWORD)
            ${N8N_ENCRYPTION_KEY} has no default (examples/n8n-postgres-compose.yaml:20,
              services.n8n.environment.N8N_ENCRYPTION_KEY)
  ...

Notes:
  - 12 findings below "medium" not shown (--severity medium); they still count for --fail-on.

Result: FAIL: 1 finding at or above "high" (--fail-on high)
$ echo $?
1
```

What the findings mean for this stack:

| Finding | Typical fix |
|---|---|
| SST-NET-001 on `postgres` | n8n reaches PostgreSQL over the Compose network, so remove the `ports:` entry (or bind it to `127.0.0.1`). |
| SST-CFG-001 | `POSTGRES_PASSWORD` and `N8N_ENCRYPTION_KEY` must be provided at deploy time. Use `${N8N_ENCRYPTION_KEY:?set N8N_ENCRYPTION_KEY}` so that Compose refuses to start without it; losing the encryption key makes stored credentials unreadable. |
| SST-OPS-001 on `n8n` | Add `healthcheck: {test: ["CMD-SHELL", "wget -qO- http://localhost:5678/healthz"]}`. |
| SST-OPS-005 on `n8n` | Replace `n8nio/n8n:latest` with a specific release and upgrade deliberately. |
| SST-RES-003 | Add json-file log rotation (see the [rule reference](rules.md#sst-res-003)) or configure it once in `daemon.json`. |
| SST-SEC-008 | The official n8n image already runs as user `node`; setting `user: node` makes this explicit. For PostgreSQL, see the image documentation before changing the user. |

The full reports are in
[`examples/reports/n8n-postgres.txt`](../examples/reports/n8n-postgres.txt) and
[`examples/reports/n8n-postgres.md`](../examples/reports/n8n-postgres.md).

## Generate a Markdown audit report

```sh
stacksentry scan compose ./compose.yaml --format markdown --output stacksentry-report.md
```

StackSentry prints a one-line status to stderr, for example `Report written to
stacksentry-report.md (12 findings)`, and writes the report with permissions
`0600`. The report contains the sections *Scan Summary*, *Target*, *Finding
Statistics*, *Findings by Severity*, *Detailed Findings*, *Scan Limitations*,
*Remediation Priorities* and *Generated By*, and can be attached to an issue,
a change request or audit documentation. Secret values are always masked. See
[`examples/reports/insecure-compose.md`](../examples/reports/insecure-compose.md)
for a complete example.

To keep the report focused, combine it with `--severity`:

```sh
stacksentry scan compose ./compose.yaml --format markdown --severity medium --output report.md
```

## Use `--fail-on high` in GitHub Actions

```yaml
name: compose-preflight
on:
  pull_request:
    paths: ["compose*.yaml", "docker-compose*.yml"]

permissions:
  contents: read

jobs:
  stacksentry:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v7
      - uses: actions/setup-go@v7
        with:
          go-version: stable
      - run: go install github.com/6-SlX-6/stacksentry/cmd/stacksentry@v0.1.0
      - name: Preflight check
        run: stacksentry scan compose compose.yaml --fail-on high --format markdown --output stacksentry.md
      - name: Publish report
        if: always()
        run: cat stacksentry.md >> "$GITHUB_STEP_SUMMARY"
```

Instead of `go install` you can download a release binary and verify it
against `checksums.txt` (see the README). Exit codes are described in
[exit-codes.md](exit-codes.md).

## Exclude a documented intentional exception

Sometimes a finding is expected. Traefik, for example, needs Docker API access
to discover containers. There are two ways to handle this.

**Per service, in the Compose file (recommended).** The exception lives next to
the configuration it explains and only affects that service:

```yaml
services:
  traefik:
    image: traefik:v3.1.6
    volumes:
      - /var/run/docker.sock:/var/run/docker.sock:ro
    x-stacksentry:
      ignore:
        - rule: SST-SEC-001
          reason: Traefik discovers containers via labels. Planned: socket proxy (OPS-142).
```

The finding moves to a *suppressed* section of the report together with the
reason, and no longer counts toward totals or `--fail-on`. Docker Compose
ignores `x-` keys, so the file stays valid.

**For the whole scan, on the command line.** Useful for rules that do not
apply to your environment at all:

```sh
stacksentry scan compose ./docker-compose.yml --exclude SST-SEC-001,SST-OPS-003
```

Excluded rules are listed under "rules not evaluated" in the report so that
reviewers can see what was skipped. Prefer the per-service exception for
security rules: a global exclusion also hides new occurrences in other
services.

## Scan a local Docker host

```sh
stacksentry scan host
stacksentry scan host --format json --output stacksentry-host-report.json
stacksentry scan host --severity medium --fail-on critical
```

The host scan connects to the daemon selected by `DOCKER_HOST` (by default
`unix:///var/run/docker.sock`; `npipe:////./pipe/docker_engine` on Windows).
For rootless Docker:

```sh
DOCKER_HOST=unix://$XDG_RUNTIME_DIR/docker.sock stacksentry scan host
```

It inspects running containers (privileged mode, Docker socket mounts, host
networking, restart policies, mutable images), stopped containers, dangling
images, Docker disk usage and TCP API listeners. It only reads data: nothing is
started, stopped, pruned or reconfigured.

If your user cannot access the Docker socket, the scan stops with exit code 2
and explains why:

```console
$ stacksentry scan host
Error: cannot use the Docker daemon at unix:///var/run/docker.sock: permission denied. Your user may not access the Docker socket. Run StackSentry as a user that can run "docker info" (membership in the docker group is root-equivalent), or set DOCKER_HOST.
$ echo $?
2
```

Information that requires more privileges than available (for example a
`dockerd` command line hidden by `/proc` restrictions) is listed under *Scan
Limitations* instead of failing the scan.
